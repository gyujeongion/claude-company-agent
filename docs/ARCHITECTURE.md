# 왜 이렇게 만들었나

## 문제

사내 AI 도입은 보통 이렇게 실패합니다.

1. **문서를 다 물려놓는다** → 답이 뭉개집니다. 재무 질문에 마케팅 톤이 섞이고,
   3년 전 폐기된 정책을 근거로 답합니다.
2. **규칙을 계속 추가한다** → 프롬프트가 길어지고, 길어질수록 뒤쪽 규칙이 무시됩니다.
3. **개인 용도를 막는다** → 아무도 안 씁니다. 업무용으로만 쓰라고 하면 하루 두 번
   열어보고 끝납니다. 손에 익지 않으면 업무 효율도 안 올라갑니다.

## 세 개의 게이트

### 1. 탐색 게이트 — 어떤 파일을 열 것인가

`CLAUDE.md`가 라우터입니다. 내용은 없고 포인터만 있습니다. 에이전트는 전체를
훑지 않고, 사람이 서랍 하나 여는 것처럼 필요한 폴더의 `CLAUDE.md`만 따라갑니다.

폴더마다 `CLAUDE.md`가 있고, 그 폴더에 뭐가 있고 언제 여는지를 적습니다.
컨텍스트를 아끼는 게 목적이 아니라, **엉뚱한 근거로 답하는 걸 막는 게** 목적입니다.

### 2. 판단 게이트 — 이 요청을 AI가 처리해도 되는가

`00_COMPANY/policy/ai_usage.md`가 요청을 A(작업)/B(판단 보조)/C(사람 결정)/X(범위 밖)/
D(개인)로 나눕니다. C는 초안까지만, X는 아예 손대지 않습니다.

이게 없으면 에이전트가 "계약상 문제없어 보입니다" 같은 답을 하게 됩니다.
그 한 문장이 회사를 망칩니다.

### 3. 경계 게이트 — 섞이면 안 되는 것

```
회사 레이어 (00~80)  ←→  개인 레이어 (90_ME)
내부 산출물          ←→  외부로 나가는 것
```

`tools/hooks/boundary_gate.py`가 프롬프트 키워드로 감지해 해당 규칙을 주입합니다.

**정직한 한계**: 이건 리마인더지 물리적 격리가 아닙니다. 같은 세션에서 두 레이어에
접근할 수는 있습니다. 완전한 격리가 필요하면 워크스페이스를 두 개로 나누고
따로 실행하세요:

```
~/AI/company/    회사 전용 (이 레포)
~/AI/me/         개인 전용 (claude-life-agent)
```

대부분의 회사에는 한 워크스페이스 + 리마인더로 충분합니다.
인사·급여 데이터는 분리가 아니라 **아예 안 넣습니다** (`policy/scope.md`).

## 개인 레이어를 넣은 이유

**도구는 손에 익어야 쓰입니다.** 주말에 개인 일정 정리하는 데 써본 사람이
월요일에 업무에도 씁니다. 업무용으로만 잠가두면 도입 자체가 실패합니다.

그래서 `90_ME/`가 있고, 통째로 git-ignore이고, 온보딩이 **"회사가 이걸 안 본다"고
먼저 말하게** 되어 있습니다. 이 보장이 없으면 사람들은 솔직하게 안 쓰고,
안 쓰면 개인 레이어는 빈 폴더로 죽습니다.

## 물리적으로 강제한 것 vs 문서로만 있는 것

| 규칙 | 강제 수단 | 강도 |
|---|---|---|
| 자격증명 접근 차단 | 훅 (PreToolUse deny) | 코드가 막음. 단 패턴 기반 |
| 개인 파일 커밋 방지 | `.gitignore` | 확정적 |
| 원본 훼손 방지 | 기본 copy, move는 플래그 필요 | 확정적 |
| 민감 파일 적재 방지 | 스캐너 + `ingest_apply.py` 강제 skip | 코드가 막음. 단 탐지는 최선형 |
| 중복 적재 방지 | 내용 해시 비교 | 확정적 (64 MB 초과는 앞부분 해시) |
| 레이어 경계 | 훅 리마인더 (문서 + 주입) | 모델이 따라야 성립 |
| 외부 발송 검토 | 훅 리마인더 + 체크리스트 | 모델이 따라야 성립 |
| 회사 사실 창작 금지 | 문서만 | 가장 약함 |

문서로만 있는 규칙은 세션이 길어지면 희석됩니다. 그래서 **사고 나면 되돌릴 수 없는
것부터** 훅으로 내렸습니다. 규칙을 더 추가하고 싶어지면, 먼저 "이건 구조로
막을 수 있나"를 물어보세요.

## 금지문 대신 절차로 쓴 이유

`"절대 ~하지 마세요"`는 대화가 길어지면 희석됩니다. 앞쪽 규칙일수록 더 그렇습니다.
반면 **"~할 때 X를 먼저 확인한다"**는 매 요청마다 실행되는 단계라 잊히지 않습니다.

그래서 이 워크스페이스의 규칙은 세 층으로 나뉩니다.

| 층 | 형태 | 예 |
|---|---|---|
| 1. 코드 | 훅·스캐너가 거부 | 자격증명 읽기, 인사 파일 적재, 경로 탈출 |
| 2. 절차 | "먼저 X를 확인한다" | 파일 열기 전 "인용할 문장이 있는가?" 자문 |
| 3. 안내 | 사실 서술 | "이 레포는 전원이 봅니다" |

**금지문은 1층에서만 씁니다.** 코드가 실제로 막고 있어서, 문서는 왜 막히는지를
설명하는 역할이기 때문입니다. 2·3층에 금지문이 보이면 절차로 바꿀 자리입니다.

직무 파일(`10_ROLES/`)에도 같은 지침을 넣어뒀습니다 — 사용자가 자기 규칙을 적을 때
"숫자를 바꾸지 않는다"가 아니라 "숫자를 쓸 때 출처 파일명을 함께 적는다"로 쓰게.

## 보장하지 않는 것

과장하면 사람들이 검증 없이 믿고, 그때 사고가 납니다. 정확히 적습니다.

- **탐지는 정규식과 휴리스틱입니다.** 자격증명·주민번호·인사 파일 탐지는 파일명과
  본문 앞부분(텍스트 계열은 미리보기 분량, PDF는 앞 5쪽)만 봅니다. 스캔 이미지 PDF,
  `.hwp` 같은 미지원 포맷, 문서 뒤쪽에만 있는 민감정보는 **놓칩니다.**
  이건 DLP·컴플라이언스 도구가 아닙니다.
- **훅은 실패 시 통과(fail-open)합니다.** 훅이 죽어서 대화가 멈추는 게 더 나쁘다고
  판단했기 때문입니다. 즉 훅은 강한 가드레일이지 샌드박스가 아닙니다.
- **훅은 이 워크스페이스에서 클로드 코드를 실행할 때만 걸립니다.** 다른 도구로 같은
  파일을 열면 아무것도 막지 않습니다.
- **레이어 경계·발송 검토는 리마인더입니다.** 모델이 따라야 성립합니다.
- **`취급:` 라벨은 접근 제어가 아닙니다.** 레포를 가진 사람은 전부 봅니다.

그래서 기준이 하나로 수렴합니다: **"레포를 가진 전원이 봐도 되는가?"**
아니면 안 넣습니다. 도구를 믿고 넣는 게 아니라, 안 넣어서 안전한 것입니다.

`bash tools/selftest.sh` 로 위 장치들이 지금 실제로 동작하는지 확인할 수 있습니다.

## 왜 폴더 이름에 번호를 붙였나

동심원입니다. 안쪽일수록 변하지 않고 자주 쓰입니다.

```
00_COMPANY   ← 업무 기준. 거의 안 변함. 매번 참조
10_ROLES     ← 내 일. 이 워크스페이스가 실제로 값을 내는 곳
20_PLAYBOOKS ← 절차. 개선되며 변함
30_KNOWLEDGE ← 자료. 계속 쌓임
...
90_ME        ← 가장 바깥. 개인. 회사와 분리
```

번호가 없으면 알파벳 순으로 섞여서 이 위계가 안 보입니다. 사람에게도,
에이전트에게도 순서가 곧 우선순위 신호입니다.

## 안 만든 것

- **부서별 폴더 전부 미리 생성** — 안 쓰는 폴더가 트리를 썩힙니다.
  실제 사용자가 생길 때 만듭니다.
- **RAG·벡터 검색** — 파일 수천 개 수준에서는 색인 카드 + grep이 더 정확하고
  디버깅됩니다. 정말 필요해지면 `30_KNOWLEDGE/cards/`가 그대로 임베딩 소스가 됩니다.
- **권한 시스템** — git 레포 접근 권한이 곧 권한입니다. 폴더를 나누거나 카드에
  `취급:` 을 적는 것은 접근 제어가 아니라 라벨입니다. 등급이 다른 자료는
  **별도 레포로 분리**하는 것만이 실제 통제입니다. 그래서 인사·급여는
  이 워크스페이스의 범위 밖으로 뺐습니다 — 통제할 수 없는 것은 넣지 않습니다.
